# Agent pending-count watch

- Added credential-free GET `agent-gateway/pending-count?watchId=<handle>`, returning only the pending JSON integer with no-store caching. Counts reuse system feed events and per-connection acknowledgements, including timeline changes and events beyond page limits. Reads have no write effects.
- Added scoped MCP/gateway `configure_agent_watch` (`changes.watch`) with shared SQL validation, connection locking, enable/rotate/disable and connection expiry/revocation/scope enforcement. Random count-only handles cannot authenticate feed reads or acknowledge changes; unknown/inactive handles return zero.
- Developer version 88 documents polling, serialized authenticated handling, backoff, host-policy limits and separate runtime activation. Added setup docs and fictional resettable demo watch interactions without account/network access.
- Validation: `npm test` passed all 871 tests (rerun outside sandbox to permit local HTTP listeners); final focused watch tests passed 3/3, covering real migrated SQL + MCP + count HTTP boundary, ownership, acknowledgements, rotation, disable, expiry, revocation, scope removal, malformed inputs and demo reset. `npm run validate:data` passed (158 roles), `npm run build` passed, and `git diff --check` passed. Feature doctor passed after npm setup recovery.
- Limits: no production migration/function deployment, hosted smoke test, live database advisors, or agent host scheduler/wake integration performed. Idle polling avoids model usage but still incurs backend request/database usage. A handle reveals activity counts to its holder and must be permitted by runtime policy. The initial sandbox test run failed on blocked localhost binds; frontend dependency installation required an unsandboxed retry after npm cache access failure.

- Follow-up: renamed the new capability to agent-neutral `configure_agent_watch`, demo methods and internal watch/count identifiers; developer version 89. Existing feed tool names remain compatible. Validation: targeted watch/feed/MCP tests and data validation.

## Agent package follow-up

- Added `agent-package/` version 0.1.0: dependency-free Node 22+ count watcher, example config, install/check/test-wake/lifecycle instructions and configurable literal-argv local wake command. The watcher omits HTTP credentials, rejects redirects and oversized/noninteger responses, bounds request/child lifetimes, uses jitter/backoff, persists wake cooldown before attempts and locks one canonical config path. It strips token environment variables from wake children and never logs URLs/child output. It does not read/acknowledge records, activate a scheduler or infer host wake support.
- Static export now packages the four allowlisted public files into `agent-package/lookout-agent-0.1.0.tgz` and publishes a SHA-256/size/version manifest. No dependency install, lifecycle hook, registry access or populated runtime config is packaged. Private local config/state/lock patterns are ignored.
- Added `read_guide {id:"agent-package"}` through the existing authenticated guide/MCP boundary and developer version 90 setup instructions. Host setup requires the existing user authorization and verified capabilities; runtime activation requires actual receipts. No new shell-execution or database-edit MCP tool was added.
- Validation: all 879 tests passed via `npm test` with local listeners enabled; `npm run validate:data` passed (158 roles); `npm run build` and `git diff --check` passed. Package tests extract the generated archive and execute its help command, verify file allowlist and archive checksum, test real child execution/failure/timeout, validate guide/MCP discovery and authorization, and drive the watcher from the detached fictional demo feed through positive/idle/error/acknowledgement/restart states. The package CLI was corrected for symlinked installation paths during verification.
- Limits: archive verified in local static output only; no frontend/backend deployment, public-download smoke test, host service installation or real runtime wake receipt. The package supports a configurable wake CLI, not a preverified adapter for every agent runtime. Crash locks require owner inspection before removal; service/worker must coalesce asynchronous runs. Idle polls still incur ordinary backend usage.

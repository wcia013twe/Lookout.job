# Programmatic single and batch application submission

- Audited the existing runner and reused its deterministic Greenhouse executor for configured Node HTTP MCP single and batch execution. No parallel form-submission engine or submission path in the search worker was added. Dedicated browser contexts/tokens are isolated per request, with two active executions maximum per process. Server-controlled `LOOKOUT_SUBMISSION_ENABLED` defaults off; discovery truthfully advertises all scopes and external side effects.
- Added bounded 1–10 application batches pinned to saved revisions. Edge/Supabase own journals, idempotent request matching, leases and per-item checkpoints; results derive from saved applications/attempts, never caller-supplied success. Active leases report busy; expired leases resume unfinished items using stable attempt IDs. Completed/partial journals replay without execution. New work after authorized repair uses a new event key/current revision. There is no background submission scheduler.
- Preserved ownership, exact-version consent, routine verified-fact policy, private file hashes, one-use submission claims and uncertain-outcome retry blocks. The real-browser audit found that fields without submitted names could be filled yet omitted from FormData; the runner now rejects unnamed, disabled or wrong-form controls before clicking.
- MCP parity: configured Node adds submit_application/submit_application_batch; read_application_batches and browser readApplicationBatches share the same owner-scoped SQL reader. Existing prepare_draft, Action Board and human review tools handle recovery. Muse directions explicitly distinguish agent-repairable pre-click issues from human-only decisions/uncertain execution. Gateway developer instructions and the application guide were versioned for the new capability.
- Demo: isolated read-only fixtures cover completed, partial/uncertain and running batches; fixture reads are independently resettable and invoke no browser or account services.
- Validation: full `npm test -- --test-concurrency=2` passes, including every database scenario, scope audit, queue ownership/version/lease/idempotency checks and Node capacity/discovery tests. `npm run test:submission:e2e` passes seven real Chromium + Node HTTP + shared Edge handler + migrated PGlite scenarios: single submission without an agent; changed-form HITL; scripted MCP agent repair from verified facts; mixed batch outcomes/replay; unnamed controls; post-click uncertainty/retry denial; interrupted-batch lease resume without duplicate submission. Frontend and Node typechecks, production static build, validate:data (158 roles), and git diff --check pass.
- Limits: employer forms, applicant facts, files and confirmations are controlled fictional fixtures. The agent is a scripted MCP client, not a live Muse/model run. Edge behavior is exercised through its shared validators/handlers and real SQL in a local HTTP fixture; this does not verify deployed Deno/Storage or an actual employer. No real application, hosted deployment, Docker rebuild, background scheduler activation or push was performed. Release the migration/gateway and configured Node image before claiming live availability. Existing local Docker stacks were not modified.
- Storage: the external SSD is the maintenance checkout/cache location required by AGENTS.md, not a hardcoded application runtime dependency. Project URLs and Node Chromium paths are server-configurable; fixture browser selection supports LOOKOUT_CHROMIUM_EXECUTABLE.

- Integration: preserved the concurrent profile-edit/typed-preference audit, reconciled shared imports/demo services/docs, and advanced the combined developer contract to 75 without replacing its profile instructions.

- Integrated verification: all 758 regression tests and the combined production build pass. The scripted agent honors the newer compact prepare_draft response and reads back the owned application record before verifying its repair.


## Profile role-to-resume mapping follow-up

- Fixed the settings/runtime gap: one selector reads the selected active profile’s Recruiting targets (title phrases plus explicit/inherited job type) and that profile’s Application materials fallback. Different matching files, invalid/missing/foreign/superseded files, malformed settings and unchecked conditions/timelines require selection/review. Legacy account rules/defaults remain only when no profile resume configuration is bound.
- prepare_draft now proposes the mapped/fallback file, pins its existing owned immutable hash for new automatic choices, and exposes compact handoff.resumeSelection metadata. Existing explicit draft files are preserved; differences from current rules require review rather than silent replacement.
- Submission context includes the current owned canonical profile/version in the existing atomic context comparisons. Routine authorization reuses the selector and rejects mismatched/stale files. Exact human approval can intentionally override mapping; no consent path was added. Existing prepare_draft and submit_application/MCP/browser paths share this behavior.
- Updated Muse developer instructions to version 78 and the application guide, clarified matching in assignment UI text, and extended isolated demo fixtures to cover unconditional mapping, fallback and conditional review.
- Validation: all 772 npm regression tests pass, including every database scenario and new profile-selection/real-SQL authorization tests. All 8 controlled Chromium/Node/Edge/SQL E2E scenarios pass; the new scenario proves both mapped and fallback choices upload their expected PDF bytes instead of the account default and saves the exact attempt file/hash. Production static build, Node runtime typecheck, validate:data (158 roles), and git diff --check pass.
- Limits: no real employer submissions, hosted migration/gateway deployment, or live Muse execution was performed. Release the profile-resume-selection migration and gateway before claiming live enforcement. Title matching is deterministic normalized phrase matching; free-text conditions/timelines remain review-required. Existing explicit/approved files are not silently changed.

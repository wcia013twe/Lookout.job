# muse-submission-blockers

- Direct submission failures now return bounded actionable blockers: fixed stage/code/message, relevant questions/field identities/choices with explicit truncation flags, current-run click/submission facts, and recovery actions. Raw exceptions, entered answers, private file URLs and credentials are excluded. Unsupported custom controls retain accessible question labels without reading selected display values.
- Queued AI Apply jobs preserve the same blocker and pending outcome/failure reports in their existing durable result. Current completion-feed pointers already lead to read_backend_jobs; application-workspace v11 describes how Muse resolves problems from Lookout/browser tools before escalating. Developer version is 98 and workflow references match. No new scheduler, wake channel, database schema or browser session transfer was introduced.
- Start-request uncertainty is recorded conservatively even when its response is lost. Unknown/existing/uncertain/confirmed outcomes never permit re-execution from the diagnostic. safeToRetry describes the current run only and still requires saved-attempt checks and current authorization. Lost confirmation reports remain reporting-only recovery.
- Demo coverage adds isolated pre-click repair and uncertain application jobs and points its existing backend completion event to a readable fictional job. Reset/read isolation remains intact.
- Validation: 918 tests passed; 27 controlled Chromium scenarios passed, including queued completion-feed read, scripted Muse repair from verified Lookout facts and one submission, initial custom-control diagnostics, uncertain outcomes and duplicate prevention. Frontend, backend runtime and intelligence typechecks, production static build, data validation (158 roles) and git diff checks passed.
- Limits: no live Muse runtime or real employer application was exercised. Browser/computer-use recovery still requires the host's tools and existing task authorization; missing personal decisions and exact human approvals remain human actions. Hosted availability needs the normal Node/gateway/config/frontend release. Nothing pushed or published; local main receives the committed change.

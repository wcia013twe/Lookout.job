# Restore sessions without flashing sign-in

- The app shell now waits for session restoration before rendering signed-out landing, login, signup, or protected-route sign-in screens. This covers the static HTML, hydration, and lazy provider fallback.
- Returning users on login/signup wait for the existing onboarding check and redirect into their workspace without briefly seeing Google sign-in. Auth and setup restoration share a neutral Loading your workspace state; startup/setup errors retain a Retry action.
- Existing persisted Supabase sessions, token refresh, explicit sign-out, non-anonymous access checks, account namespaces, and public reference routes remain authoritative. No cached identity is used to grant access and no backend/auth policy changes were introduced. Existing human Google OAuth/sign-out boundaries and scoped MCP account ownership remain unchanged; this is a website rendering change, not a new service action.
- Validation: full suite 948 passed, 5 skipped; frontend typecheck; production static build/export; data validation (158 roles); browser checks with real Supabase client and fictional intercepted API responses across five routes and reloads, zero sign-in flashes, delayed expired-token recovery, persistent sign-out, guest access restrictions, public privacy access, demo reloads, and mobile overflow. Desktop restoring and mobile restored screenshots inspected.
- Demo coverage: existing detached demo was exercised through navigation and reload without altering its fictional data or account access. No new demo fixture content is needed for a session-loading state.
- Verification limits: browser auth responses were intercepted; no live Google OAuth or production deployment was performed. Verification logs/screenshots are on the external SSD under Lookout/tmp/restore-session-verification.

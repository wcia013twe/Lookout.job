# Lookout data layer: UI-first design review

**Proposal, not an implemented schema.** This design comes from a source crawl of every UI route, nested workspace and shared dialog at baseline `d1a87679e2c53f3c5d10b953dd62ca91de9b57e1` (2026-10-22). Three subagents gathered requirements and reviewed the synthesis. No current database schema, migrations, hosted records or private user files were used as the design authority.

Open [the editable ten-sheet draw.io file](lookout-data-layer.drawio). Start at **00 Relationship graph**, then **00a UI and AI content flow**, **00b Document and AI fields**, and the seven domain ERDs. [Browser editor links](editor-links.md) open the individual sheets. [The field dictionary](dictionary.md) records fields, optional relationships and constraints; [the UI evidence map](requirements.md) connects the model to screens. The diagram is a relational graph, not a recommendation to add a graph database.

The earlier `lookout-schema.drawio` is superseded by this document-based revision and is retained because the shared checkout contains an editor-modified copy. Open `lookout-data-layer.drawio` for the current design.

## Personal agents own inference

The user’s personal agent reads context through scoped MCP, performs research and reasoning in its own runtime, and writes useful results back. Lookout stores context, validates ownership/permissions/versions, coordinates handoffs and displays saved outputs. AgentTask is a request/claim/outcome inbox, not an internal inference executor. AgentCheckpoint records consumed context/feed positions, not model reasoning steps.

The initial schema excludes inference orchestration, model registries, provider/model/recipe metadata, prompt-execution histories, reasoning logs, generation ancestry and per-field text hashes. Preserve document author/time, optional sources and input-version references; use ordinary last-editor metadata on mutable records. Resume/blob checksums, exact approval digests and submission evidence remain because they protect material integrity and authorization rather than describe inference.

## Decisions that remove duplication

1. **Company → Job → Posting.** Company identity is shared. A job is an employer requisition/cycle; several verified URLs may identify it. Discovery occurrences, personal fit and applications reference that job instead of copying a new job per source, batch or user.
2. **One Application per owner/job.** Tracker and preparation share one identity. Opened time, recruiting stage and preparation state are separate. Opening a link is not applying; queuing is not opening. The Auto Tracker query requires `opened_at`, while Applications may also show queued records.
3. **One CandidateProfile, many profile documents.** Verified candidate facts and reviewed answers remain structured. Preferences, writing guidance and evaluation rules share the existing canonical Markdown/YAML profile boundary. The UI patches named fields; the server validates and derives rebuildable query projections. Full prose remains available to the agent. Effective execution permissions are separate, typed and profile-specific. A duplicated profile does not duplicate a résumé or identity or grant permissions.
4. **One Document library with immutable versions.** Profile documents, source configuration, AI analysis, résumés, letters, templates, toolkit artifacts, debriefs and collection manifests share storage/version mechanics, with kind-specific validators. Profile sections select existing materials/answers; draft creation pins exact versions. Long AI text is a linked document, while short rationale stays on its domain record with ordinary last-editor metadata. There is no table per analysis type.
5. **One Contact, many Conversations.** A person is not a company target or a referral status. Company research is separate. Messages/meetings become independently growing rows rather than JSON serialized in contact notes. Conversation-to-application links replace magic tags and URL guesses.
6. **One Post + PostRevision model for Circles.** Chat, resources, experiences, offers and updates are typed projections. Shared content is an intentional immutable disclosure snapshot, never a live join into private candidate records. Agent-reported helpful use comes from receipts, not a duplicate reaction counter.
7. **Tasks/sessions are facts; agendas are views.** A preparation plan can target an application or represent a learning goal. One practice session can credit several tasks while its actual duration counts once. No second copy of the weekly calendar is stored.

## Why this is still lean

The revision reduces **49 → 44 relations** and **560 → 536 individually listed top-level fields**, while adding explicit AI provenance and document-subject links. The new nested-content sheet also shows the fields inside profile/source/analysis/collection contracts. This is a logical target, not a request to create all tables at once.

| Removed relation | Canonical replacement |
|---|---|
| SearchProfile | Document(kind=search_profile) + immutable DocumentVersion; parsed current-version projection is rebuildable. |
| ProfileAnswer | Bounded, deduplicated `Application materials / Saved answer IDs` in that profile; referenced SavedAnswer rows keep their own review policy. |
| ProfileMaterial | Default resume selection + bounded `Recruiting targets / Targets` entries in that profile. Assignments follow a stable document; actual draft pins a version. |
| SearchSource | One current owned source-config document with bounded sources, queries and filters; runs pin a version. |
| CollectionItem | Ordered, validated pinned references owned by the collection version; no independent item lifecycle. |

Long `CompanyTarget.research` and its source list move to a linked analysis document; the UI Research field reads/writes that body. No duplicate research text remains on the target. All candidate evidence, saved answers, tier-list membership, applications, approvals, receipts, contacts and growing histories retain their structured boundaries.

This borrows Career Ops’ separation of **candidate evidence / preferences and voice / procedures / source configuration**, while reusing Lookout’s existing document writer rather than introducing a second file-backed tracker. Existing source: [document serialization](../../lib/search/documents.mjs), [named UI fields](../../lib/search-profile.mjs), [recruiting targets](../../lib/recruiting-targets.mjs), [search context contract](../search-context-and-sweeps.md). This design does not make the whole app a Markdown database.

Keep bounded, atomically edited structures as validated document sections or JSON. Retain separate rows for independently growing conversations, versions, attempts and memberships. Do not build a universal entity/property/value system, table-per-checkbox, global contact graph, generic SQL tool or universal activity table that mixes submission proof with chat. See [the complete document/AI contracts and UI examples](document-contracts.md) for limits and reference validation.

Do not persist derived UI as independent truth: route names, active tabs, form drafts, completion warnings, initials, copied prompts, rarity labels, pending-action counts, application progress bars, waiting-for-reply flags, leaderboard totals, weekly agenda, artifact routes, or Circle channel memberships. The static toolkit skill catalog stays in files. Theme marketplace selection is visit-local. Guest/browser XP and pack/seen state remain device-local in the initial design; they are not authoritative account leaderboard input. Demo fixtures remain isolated in memory, not production rows with a demo flag.

`PostPublication` is a small technical change log justified by cursor-based feed invalidation and withdrawal handling. It is not a second copy of post bodies. If the implementation retains polling initially, defer this table until the cursor feed is shipped; the publication transition still needs to be atomic.

## Identity, uniqueness and relationship rules

- UUIDs are stable identities. Company names are labels. Verified aliases are unique within their namespace; ambiguous aliases are not silently attached to an existing company. Unresolved private company targets/contacts/answer scopes stay private until resolution.
- Job dedupe order: normalize canonical employer/ATS URL while preserving requisition parameters; match provider/requisition identity; then compare normalized company/title/location as a **candidate duplicate**. Distinct requisitions and hiring cycles must survive. Record and review ambiguous matches. On a confirmed merge, redirect aliases/references transactionally; coalesce duplicate owner/job rows without losing status, events, drafts or attempts.
- Do not conflate global saved answers with unresolved company-specific answers. `scope_kind` and `scope_key` distinguish global, resolved company and unresolved company scope. Uniqueness is `(owner, exact_normalized_question, scope_key)`, including an explicit global key; fuzzy matches only propose reuse.
- Every private child reference must resolve under the same owner. Carry owner on children where needed for composite foreign keys `(owner_id, parent_id)` and row access checks; the diagram omits repetitive account wires. User IDs supplied by a client never establish ownership. Actor/author/reporter fields refer to real account or connection identity, with actor-kind checks.
- Composite FKs: DraftRevision `(application_id, revision)`; Authorization and SubmissionAttempt `(application_id, draft_revision)`; selected résumé `(document_id, version_no)`; SearchRun profile/source document-version pairs; SelectionDecision profile document-version pair; DocumentLink profile document-version pair; collection manifest child document/version references are service-validated, not SQL foreign keys; PostRevision `(post_id, revision)`; publication/receipt `(post_id, revision)`. Validate that an attempt's authorization is for the **same application, revision and digest**.
- Current/reviewed version pointers on Document and current/published pointers on Post must reference an existing revision of that same parent. Document review requires the actual human reviewer and applies only to that revision; it is editorial review, never a fact verification or execution grant. Document(kind, key) is unique within owner when key is set. Legacy profile string IDs map to Document.key; other relational IDs remain UUIDs. A current source-config document is unique per owner. A new private post draft never replaces the currently published revision. Snapshot-linked values remain immutable; title/head metadata on Document is a projection of the current version. Projection and projection_version_no update atomically with current_version_no; no projection-only writes. Archived documents retain historical versions and cannot be selected for new work.
- SourceObservation.posting, when set, must belong to its job. A SelectionDecision must reference the same observation/job and owner/profile as its run. BatchItem decision must match its job and private owner. Public batches cannot point to private decisions. Public runs/batches have null owner; private ones require owner. Owner-null is an explicit scope check, not an authorization shortcut.
- PrepPlan has at most one current application plan per owner/application; standalone learning goals use the plan ID and required goal title. PracticeCredit resolves task/plan/owner and expected revision atomically. One session's elapsed minutes is counted once even if several targets receive credit.
- DocumentLink has exactly one typed target: application, round, plan, task, company target, job, selection decision, contact, conversation, search run, or profile document/version pair. A version pair counts as one target; both components must be set together. Multiple subjects use multiple rows. Validate profile kind and same-owner private targets; job links remain owned even though the job is public. Collection references require same owner and pinned versions, disallow cycles and duplicate child/version. Embedded profile/collection references do not have automatic FK enforcement: validate atomically at save and use, prohibit destructive deletion of referenced versions, and use indexed derived dependencies if reverse lookups become expensive.
- CompanyTarget is unique per owner/resolved company. Contact identities can match exact verified email or canonical LinkedIn within the owner; names/company alone are review candidates. CompanyTarget-to-contact/application lists are queries, not copied ID arrays. Explicit conversation/application joins preserve process isolation.
- CircleMember is unique per circle/account and records removal time. Exactly one active owner; transfer atomically. CircleInvite records issuance, expiry and revocation; a removed member needs an invitation issued after removal. The UI shows invite tokens: prefer one-time presentation or recoverable encrypted secret if redisplay is retained, never a plaintext database token. Invite hash verifies redemption.
- Replies, publication events and revision references must remain in the same circle. Membership and current visibility are checked on every read. Personal/agent-drafted disclosures require approval of the exact revision. Restricted resource/opportunity templates may publish only under explicit membership policy and validated no-personal-data rules; this is not blanket permission for agent-authored posts.
- AgentReceipt remains private to its consumer. Helpful people is a distinct eligible-user count from active use receipts; it is not confirmed benefit. Withdrawal/hiding/removal changes source availability without exposing private reference text.

## Lifecycle and evidence

Recruiting stages and preparation states use separate canonical enums with UI/legacy label mappings. Suggested recruiting progression: New → Applied → OA/Phone screen/Interview/Onsite → Offer/Rejected/Withdrawn (not every role follows every stage). Preparation: unprepared → draft → needs review/blocked → authorized → executing → confirmed/uncertain/failed. These are separate axes, not one universal status column. Historical self-reports are retained as claims with provenance.

A new draft revision invalidates previous authorization for execution. An approval, a policy decision and a validated employer receipt are three different facts. Routine policy authorization also rechecks verified facts, selected materials, answer provenance and runtime capability. An atomic claim binds one attempt to one authorized revision; only one active attempt per application. A used/expired permit cannot click again. An uncertain outcome blocks retry until explicit resolution. Current profile data can be shown as context but must never backfill an old submitted form snapshot.

An ApplicationEvent round reference must belong to that same application. PostRevision content is immutable; its approval metadata is a one-way, audited attestation and cannot edit the disclosed content. ApplicationEvent captures append-only claims/observations and transitions. InterviewRound is the editable scheduled-round record with event history; do not represent its date as the preparation deadline. Date-only records remain dates; unknown dates remain null. Interview debriefs are ordinary private versioned documents with typed application/round links. Share-to-Circle prepares a separate reviewable disclosure; it does not publish the private document automatically.

Onboarding has an independently versioned session and task inbox. The UI displays connection → intent → first match → policy → profile prerequisites/execution → delivery → ready, with pause/resume and uncertain reconciliation. Exact transition validation needs a later contract review. Issuing a connection or saving a routine does not prove execution or scheduling is connected.

## Access, scale and retention

Use ordinary relational joins and indexed read projections first. Public company/job/posting facts are readable independently of private fit. Account-owned data is private; Circle access is membership-based; the public leaderboard contains only opted-in alias and aggregates. Object storage serves private document blobs with short-lived owner-checked access. Do not persist signed URLs. Blob dedupe is within an owner/security boundary; do not use cross-user hash matches to leak file existence.

Baseline indexes should follow queries, not every JSON key:

- Posting canonical URL and `(provider, external_id)` where present; CompanyAlias namespace/key; Job company/type/state.
- Application unique owner/job plus `(owner, recruiting_stage, updated_at, id)`; events/attempts by application/time/id.
- Run by owner/created_at/id; observations by run/observed_at/id; decisions by owner/profile/decision; batch items by batch/position.
- Documents by owner/kind/archived/updated_at/id; revision composite keys; typed link target indexes; optional full-text index on actual toolkit search fields.
- Prep tasks by plan/state/due date; sessions by owner/completed time; interactions by conversation/date/id; follow-ups by owner/due date.
- Circle membership; posts by circle/visibility/created time/id; searchable published revisions only; publication sequence per circle; receipts by owner/source and source/consumer.
- Tasks by owner/state/created time; unique owner/event key and a filtered active-claim constraint. Expired/revoked connection checks are mandatory.

Use stable keyset cursors for large histories. Bounded JSON is reasonable for profile backgrounds and form snapshots; unbounded conversations, attempts, revisions and feed events stay rows. Materialize expensive aggregate views only after measuring. Start with a single relational store and object storage; partition high-volume append-only observations/events only when measured volume warrants it. No graph database, event-stream platform or warehouse is required by these screens.

Account leaderboard metrics should derive from server-owned application/event facts under a documented scoring policy; browser XP is not trusted input. If account-wide pack rewards are later introduced, add an idempotent reward fact then, rather than guessing a reward subsystem now. Do not mix verified submissions with self-reported outcomes in metrics that claim verification.

Archive jobs/documents/contacts still referenced by evidence; prevent cascade deletion from destroying historical submissions. Withdrawal removes shared visibility; account erasure requires a deliberately specified retention/redaction policy for private files, evidence and authored Circle posts. The UI does not establish legal retention durations, so none are invented here. This is an implementation decision to resolve, not an existing export/deletion feature.

## UI and agent service boundaries

This is documentation only: no new user actions or MCP tools were implemented, and no deployed parity is claimed. The eventual service layer must expose the same ownership, validation, revision and idempotency rules to website and scoped MCP operations. Existing frontend-visible mappings provide the starting point:

| Domain | Observed scoped boundary / future implementation requirement |
|---|---|
| Search/discovery | Search context, request, run read, discoveries read, selection decision read/reconsider, publish batch. Persist canonical jobs separately from owned assessments. |
| Profile/materials | Versioned document section patch, profile/settings save, profile package, résumé upload/source replacement, saved-answer review, document/artifact list/read/save/archive. The UI projection is derived from the canonical document. Policy edits require a separate human action boundary. Existing APIs need kind-specific validators before consolidation; this is not a new generic write-anything tool. |
| Applications | Prepare draft, read exact approval, website human approval, stage report, read submission record, resolve uncertain attempt, record milestone. Agents cannot forge human approval or receipt. |
| Preparation | Read plan/planner, save budget, complete session, artifact links. One same-owner, version-checked session operation credits all targets. |
| Network | Versioned company/contact/conversation save, outreach preparation request. Logging and drafting do not send external messages. |
| Circles | Propose/edit/read, exact publication/approval, withdraw, report/hide, membership/invites, policy settings, citation receipts. Never expose private join data through these reads. |
| Agent/onboarding | Scoped credential lifecycle, context versions, onboarding step, task request/claim/outcome. Human-only boundaries must be explicit; no generic database edit tool. |

## Delivery and verification

The official [draw.io MCP server](https://github.com/jgraph/drawio-mcp/blob/main/mcp-app-server/README.md) was called via its Streamable HTTP endpoint using `initialize`, `tools/list`, `get_drawio_reference(xml)` and `create_diagram` for every sheet. This session did not expose draw.io as a registered tool, so the calls used a direct MCP client over HTTP; no user configuration was changed. The server returned editable diagram XML and editor links. This is distinct from claiming an inline MCP app was embedded in this conversation.

`full_fields.py` owns the individual field definitions; `document_contracts.py` adds the UI flow and nested document contracts; `build_diagrams.py` owns relationship definitions, notes and layout. It deterministically generates `model.json`, `dictionary.md`, `lookout-data-layer.drawio` and temporary per-sheet input. It is not runtime schema code. Regenerate with `python3 docs/schema-review/build_diagrams.py`. Then run `route_diagrams.mjs` with `DRAWIO_MCP_ROOT` pointing to an external installation of official `@drawio/mcp@1.10.0` and `XDG_CACHE_HOME` on the external SSD; this applies obstacle-avoiding routing to the native file. The app dependencies are unchanged. Recreating remote editor links is a separate MCP operation. The proposed physical migration remains unbuilt and untested. Data/XML/reference validation and browser rendering results are recorded in the change note. Existing runtime/demo fixtures were not changed because this pass changes no product behavior.

# Discover application jobs

Discover has two actions: **AI Apply** submits a durable application job and becomes **Queued**; **Open Application** opens the employer posting without changing tracking state. The title opens the existing preview. Queueing, opening, running, failure and uncertainty do not remove the posting. Only recorded applied/submitted progress hides it from the latest Discover view. Recorded human progress remains distinct from runner-observed confirmation.

Applications resolves legacy opened IDs against both the owned batch and public catalog, so public roles outside the current batch remain visible under Saved jobs. Shared canonical URLs prefer the owned application when the historical opened ID differs from the backend ID. No candidate record is deleted or marked applied by this repair.

Website `queueApplicationJob` calls `queue_application_job(payload)`; MCP `queue_application_job` maps to `applications.submit_job`. Both use the same closed SQL helper. It validates a bounded selected canonical Greenhouse posting, creates/reuses its canonical catalog identity and owned application, pins the current revision/profile, and deduplicates active jobs. An active owned execution connection with workspace:read, preferences:write, drafts:write, approvals:read and resumes:read is required. Website requests select the most recently created eligible owned connection; MCP uses its authenticated connection. The click grants task intent, never exact human approval or verified facts. Exact retry keys return their original receipt; use current application execution state or read_backend_jobs for progress.

The existing private backend queue now permits application_submit internally. Generic search submits cannot create this kind. `applications.execution_job` is a server-controlled projection of queue transitions, visible only under existing application ownership. Existing workspace invalidations refresh the UI without a panel polling timer.

A submission-enabled Node worker claims application work separately from search. Each SQL call is fenced by job ID, version, five-minute lease, active connection and pinned application. The worker inspects an empty supported form, calls the existing deterministic prefill/profile-to-resume selector and preserves existing approved drafts. It runs no LLM. Unsupported fields and missing personal choices use the existing failure/HITL path. Submission reuses shared authorization, atomic claim, one-use click permit and observed receipt persistence. The stable attempt ID is job-{UUID}; an expired job lease cannot authorize a second Submit click. No raw agent token is stored in a job.

Set both LOOKOUT_EXECUTION_ENABLED=true and LOOKOUT_SUBMISSION_ENABLED=true on the configured worker to consume application jobs. Disabled submission workers leave these jobs queued. Queue receipts do not prove a running worker. Current submission support remains native Greenhouse forms/PDF resume; no arbitrary URL execution, CAPTCHA bypass, agent reasoning, approval or sharing is added.

Muse receives the updated developer instructions and tool discovery on its next authorized context refresh. Finished backend jobs use the existing Muse change feed; this does not wake Muse or create a schedule. After supported preparation repair, request a new job using the current revision. Uncertain attempts require the existing human verification path first.

Demo queueing is isolated, fictional and memory-only. Open Application is inert there; no employer submission, account access, private file read or production request occurs. Normal database, gateway/MCP, Node worker and frontend release is required for hosted availability. Controlled local browser fixtures do not establish real employer or live Muse operation.

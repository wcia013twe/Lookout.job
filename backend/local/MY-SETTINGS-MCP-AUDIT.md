# My Settings MCP audit

Read-only source audit, 2026-10-26. Existing persistence mostly works; the primary gaps are typed field coverage and safe edits of labeled text. Findings do not establish hosted deployment or authorize additional service migration.

- **Personal facts:** UI `lib/profile-schema.js` includes preferredName, suffix, birthday, address, address2, address3 and postalCode. Typed import/update vocabulary in `supabase/functions/agent-gateway/write-schemas.mjs` and SQL `20261023044924_agent_field_updates.sql` omits them. Generic save_profile_facts replaces the full facts object and is not a safe substitute for a typed partial update. Unify the field vocabulary and validation while retaining current owner/version checks.
- **Writing preferences:** `next-app/components/profile-settings.tsx` exposes employer-answer and outreach Tone/Length/Guidance. They are labeled Markdown in each profile's instructions, edited by `lib/search-profile.mjs`. Whole-profile MCP saves exist, but duplicate labels and out-of-range writing values can pass. Add a shared typed parser/composer and narrow versioned patch over the same canonical profile; do not add a second settings table. These preferences do not define how Muse speaks to the user.
- **Eligibility and targeting:** country-specific authorization, sponsorship and availability are labeled text. Employment and Work arrangement are structured string filters that may contain comma-separated choices. MCP whole-profile saves do not enforce all UI country-reset/consistency behavior. Preserve freeform exceptions but share typed values, priority, duplicate detection and country-reset rules across entry points.
- **Profile editing:** roles, specializations, industries, company size, skills, benefits, goals, tradeoffs, rules and Required/Preferred/Flexible weights are mostly labeled text. Updates must preserve unrelated prose and current versions. Existing profile/document saves converge into canonical search_documents; no new store is needed.
- **Identity:** facts.preferredName and legacy Application identity preferred-name labels are used inconsistently by overview helpers. Define canonical precedence and adapt historical labels without dropping data.
- **Materials:** private résumé upload/read and versioned artifacts already exist. Per-profile résumé assignments are JSON embedded in Recruiting targets / Targets; expose a narrow patch using its existing parser instead of making agents replace unrelated narrative/targets.
- **Local intake:** runner/gateway-client.mjs and runner/profile-upload.mjs hardcode the hosted project origin. A trusted server-configured origin/public key must also govern strict signed upload/download URL validation. Never take destinations from tool callers.
- **Discovery metadata:** instructions.json still advertises capabilities.preferenceWrites=false despite existing scoped preference tools. Correct this with explicit limitations and a developerVersion increment when the settings fix ships.
- **Existing boundaries to preserve:** profile changes invalidate verification; imported answers remain ask-policy/unverified; approvals, sharing grants and connection management remain separate human actions. Device appearance mode is intentionally browser-local. Owned artifacts, search sources and existing routine/theme preferences already have scoped routes; saving a schedule does not activate execution.

No files or account records were changed by the delegated audit. Minimum follow-up is shared settings validation and narrowly scoped version-preserving adapters over existing records. Implementation remains separate from this audit and the planned résumé parsing service.
